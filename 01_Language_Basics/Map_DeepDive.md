# Go Map: Deep Dive & Internal Architecture

## 1. Ментальная модель и Концепция

map в Go — это хеш-таблица. В отличие от простых языков, где хеш-таблица — это массив пар key-value, в Go используется цепочка бакетов (buckets) с механизмом разрешений коллизий через Overflow Buckets и Инкрементальный эвакуационный эвакуатор (Evacuation / Growing).

Коллизия в map на Go происходит, когда два разных ключа дают одинаковый или пересекающийся хеш.

## 2. Анатомия Map до Go 1.24 (Классическое устройство)

Под капотом переменная map — это указатель на структуру hmap (runtime/map.go).

```
hmap (Header)
├── count      : количество элементов
├── B          : log2 от количества бакетов (2^B бакетов)
├── hash0      : рандомная соль для хеш-функции (защита от HashDoS атаки)
├── buckets    : указатель на массив бакетов (2^B)
├── oldbuckets : указатель на старый массив бакетов (при рехашинге)
└── nevacuate  : прогресс эвакуации (индекс следующего бакета)
```

### Анатомия бакета (bmap)

Каждый бакет умеет вмещать ровно 8 пар key-value.

```
bmap (Bucket Layout)
├── tophash    : [8]uint8 (старшие 8 бит хеша каждого ключа)
├── keys       : [8]KeyType
├── values     : [8]ValueType
└── overflow   : *bmap (указатель на следующий overflow-бакет при коллизии)
```

#### Почему keys отдельно от values? Память упаковывается как [K1..K8][V1..V8], а не [K1 V1][K2 V2]?

-   Это сделано для избежания лишнего padding (выравнивания памяти в байтах), если типы Key и Value имеют разный размер.

## 3. Алгоритм поиска элемента (How Lookup Works)

-   Вычисляется 64-битный хеш ключа: hash = hashFunc(key, hmap.hash0).

-   Определяем бакет: берутся младшие B бит хеша. Это индекс бакета в массиве buckets.

-   Определяем ячейку в бакете: берутся старшие 8 бит хеша (tophash).

-   Runtime сначала сравнивает байт tophash. Если совпал — проверяет полное равенство ключа key == targetKey.

-   Если в текущем бакете ключ не найден, Go переходит по указателю overflow в следующий переполненный бакет.

## 4. Рост, Переполнение и Рехашинг (Map Growing)

Map начинается с малого количества бакетов. Как только нагрузка возрастает, происходит Growing (рост).

### Факторы срабатывания роста:

1. Load Factor > 6.5: Среднее количество элементов на один бакет превышает 6.5.

    - Решение: Выделяется новый массив бакетов в 2 раза больше (2^(B+1)).

2. Слишком много Overflow Buckets: Элементов мало (часто удаляли через delete()), но создано много overflow-бакетов.

    - Решение: Размеры массива не увеличиваются (2^B), происходит Same-size growing — «утряска» и очистка памяти от фрагментации.

### Инкрементальная эвакуация (Инкрементальный рехашинг)

Go не переносит все элементы сразу, чтобы не вызывать больших задержек (Stop-the-World/Latency Spikes).

-   Создается массив oldbuckets, куда сохраняется ссылка на старые бакеты.

-   При каждой операции записи (map[k] = v) или удаления (delete) Go переносит 2 старых бакета в новый массив.

-   Пока идет эвакуация, операции чтения сначала смотрят в oldbuckets, а потом в buckets.

## 5. Что нового в Go 1.24? (Swiss Tables)

В Go 1.24 произошел исторический сдвиг — традиционный hmap/bmap заменен на архитектуру Swiss Tables (адаптация разработки Google).
Что изменилось и почему это спрашивают на собеседованиях?

-   SIMD Инструкции: Вместо последовательного перебора 8 элементов tophash с помощью обычного цикла, Swiss Tables использует SIMD-команды процессора, позволяя проверить совпадения в групповом мета-массиве (Group Control Bytes) за 1 тактовую инструкцию процессора.

-   Снижение потребления памяти: Использование плотных мета-групп сократило накладные расходы по памяти в среднем на 20-30%.

-   Улучшение Cache Locality: Метаданные хранятся отдельно и компактно, благодаря чему L1/L2 кэш процессора не забивается неиспользуемыми ключами при поиске

### Что такое SIMD? 💡

SIMD расшифровывается как Single Instruction, Multiple Data (Одна инструкция — много данных).

Обычный процессор (SISD): Работает как кассир, который сканирует товары по одному. Чтобы проверить 8 ячеек tophash, процессор берет 1-й элемент, сравнивает, затем 2-й, сравнивает... Делает 8 циклов.

SIMD-процессор: Имеет широкие регистры (например, AVX2 / SSE2 на x86 или NEON на ARM). Он загружает все 8 (или 16) байт сразу и сравнивает их с искомым значением за 1 тактовую инструкцию процессора.

Обычный цикл (До Go 1.24):
[Шаг 1: check tophash[0]] -> [Шаг 2: check tophash[1]] -> ... -> [Шаг 8]

SIMD подход (Go 1.24 / Swiss Tables):
[Загрузка всех 16 tophash в SIMD-регистр] ──(1 инструкция)──> [Маска совпадений: 00010000]
▲
Совпадение на 4-й ячейке!

### Почему Swiss Tables с SIMD работает быстрее? 💡

-   Параллельное сравнение: В Swiss Tables метаданные (байты управления) хранятся компактными группами по 16 байт. SIMD-инструкция проверяет сразу весь блок за один запуск.

-   Меньше промахов кэша (Cache Misses): Кэш процессора считывает массив метаданных молниеносно, не забивая L1/L2 кэш тяжелыми ключами и значениями.

### Итог:

- ✒️ **SIMD (Single Instruction, Multiple Data):** Аппаратная возможность процессора выполнять одну математическую/логическую операцию над векторным массивом данных одновременно.

- ✒️ **Применение в Map:** Вместо последовательного перебора 8 элементов `tophash` в цикле, Go 1.24 загружает вектор метаданных (16 байт) в SIMD-регистр и находит нужный индекс **за 1 тактовую инструкцию процессора**.

- ✒️ **Результат:** Прирост скорости поиска и снижение потребления памяти на 20-30%.

## 6. Шпаргалка по Edge Cases

-   Потокобезопасна ли map?

    -   Нет. При одновременной записи и чтении/записи без мутекса runtime выбросит неперехватываемый фатальный сбой: fatal error: concurrent map read and map write.

-   Можно ли взять адрес элемента &m["key"]?

    -   Нет. Из-за инкрементального рехашинга элементы постоянно меняют свое физическое местоположение в памяти.

-   Что вернет чтение несуществующего ключа?

    -   Zero-value типа значения (например, 0, "", nil). Вторая переменная-флаг покажет существование: v, ok := m["key"].

-   Освобождает ли delete() память?

    -   Нет. delete() очищает ячейку в бакете, но память массива бакетов остается выделенной процессом. Единственный способ уменьшить занимаемую память — создать новую map и скопировать данные.

-   Какой тип может быть ключом в map?
    -   Только comparable типы (те, к которым применима операция ==). Слайсы, мапы и функции не могут быть ключами.
