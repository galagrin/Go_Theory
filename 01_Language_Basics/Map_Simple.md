# Go Map: Deep Dive in Simple Example

## 1. Как работает Хеш-функция? (Превращаем ключ в число)

Когда ты делаешь m["cat"] = "кошка", Go не умеет искать по слову "cat". Ему нужно превратить слово "cat" в длинное уникальное число.

Для этого Go использует специальную математическую функцию (хеш-функцию). Она берет строку "cat" и превращает ее в 64-битное число (длинную цепочку из 0 и 1).

Для наглядности представим, что хеш-функция превратила слово "cat" вот в такое число:

11010010 00000000 00000000 00000000 00000000 00000000 00000000 00000101

Чтобы не сойти с ума от нулей и единиц, разрежем это число на две части:

-   Старшие биты (самый левый край): 11010010 (первые 8 циферок).

-   Младшие биты (самый правый край): 00000101 (последние циферки).

## 2. Зачем нужны МЛАДШИЕ биты? (Ищем нужный шкаф/бакет)

Представь, что в нашей мапе сейчас 8 бакетов (шкафов), пронумерованных от 0 до 7.

Go смотрит на МЛАДШИЕ (самые правые) биты хеша.
Младшие биты 00000101 в двоичной системе — это число 5 в обычной 10-тичной системе.

⚡ **Вывод: Go моментально понимает: «Так, пара "cat" -> "кошка" должна лежать в бакете №5!»**

Младшие биты нужны ТОЛЬКО для того, чтобы среди тысяч бакетов сразу открыть нужную «дверцу шкафа» и не перебирать все подряд.

## 3. Зачем нужны СТАРШИЕ биты (tophash)? (Ищем среди 8 вешалок)

Вот Go открыл бакет №5. Внутри этого бакета висит 8 вешалок. На них уже могут лежать какие-то другие данные.

Как быстро узнать, на какой из 8 вешалок висит наш "cat", не сравнивая каждый раз тяжелую строку "cat" с имеющимися?

Для этого Go берет СТАРШИЕ (самые левые) 8 бит хеша (в нашем примере 11010010, это число 210). Это число называется tophash.

В бакете есть крошечный массивчик из 8 чисел. Go просто пробегает по 8 байтам:

    - На вешалке 1 лежит tophash = 12? Нет, не то.

    - На вешалке 2 лежит tophash = 45? Нет, не то.

    - На вешалке 3 лежит tophash = 210? СОВПАЛО!

И только когда tophash совпал, Go делает финальную полную проверку: смотрит на ключ на вешалке 3 и проверяет: key == "cat".

⚡ **Вывод: СТАРШИЕ биты (tophash) нужны для супер-быстрого поиска внутри одного бакета среди его 8 элементов, чтобы не сравнивать строки/структуры напрямую, а сравнивать быстрое маленькое число (1 байт).**

## 4. Пошаговый поиск: Алгоритм «на пальцах»

Когда ты пишешь val := m["cat"], происходит следующее:

-   Хеширование: hashFunc("cat") -> получаем 64-битный хеш.

-   Поиск бакета: Смотрим на младшие биты хеша -> узнаем номер бакета (например, бакет №5).

-   Поиск внутри бакета: Смотрим на старшие биты хеша (tophash). Пробегаем по 8 ячейкам бакета №5 и сравниваем tophash.

-   Финальное сравнение: Если tophash совпал, проверяем сам ключ "cat" == storedKey.

-   Если совпало: Возвращаем значение "кошка".

-   Если не совпало и бакет кончился: Если в бакете №5 не нашли, смотрим на указатель overflow. Если там привязан дополнительный бакет-переполнение, идем в него и повторяем шаги 3-4.

## 5. Почему в бакете keys хранятся отдельно от values?

Давай сравним два способа положить данные в память.
Способ «как кажется логичным»:

Хранить парами: Key1, Value1, Key2, Value2 ...

    Представь, что ключ — это int8 (занимает 1 байт), а значение — это int64 (занимает 8 байт).

    Из-за правил процессора (выравнивание памяти / padding) процессор будет вынужден вставлять «пустые дыры» в 7 байт после каждого int8, чтобы int64 встал ровно. В итоге мы теряем кучу памяти впустую!

Способ Go:

Хранить блоками: [Key1, Key2 ... Key8] [Val1, Val2 ... Val8]

    Сначала идут все 8 ключей подряд, затем все 8 значений подряд.

    Никаких «пустых дыр» (padding) между ключами и значениями не возникает. Память утилизируется максимально эффективно.

# Анатомия и Поиск в Go Map (Простыми словами)

## 1. Зачем разделять Хеш на Старшие и Младшие биты?

Хеш (64 бита) делится на две части:

-   **Младшие биты (справа):** Вычисляют **НОМЕР БАКЕТА**. Направляют запрос в конкретный бакет из массива `buckets`.
-   **Старшие биты / `tophash` (слева, 8 бит):** Вычисляют **ЯЧЕЙКУ ВНУТРИ БАКЕТА**. Нужны для быстрого сравнения 1 байта памяти вместо сравнения тяжелых ключей.

## 2. Пошаговый алгоритм поиска `m[key]`

1. Считать 64-битный хеш от ключа.
2. По **младшим битам** найти индекс бакета.
3. По **старшим битам (`tophash`)** быстро пробежать по 8 ячейкам бакета.
4. При совпадении `tophash` точечно проверить равенство ключа: `key == stored_key`.
5. Если в основном бакете не нашли — перейти по указателю `overflow` в следующий бакет-переполнение.

## 3. Упаковка памяти в бакете (`bmap`)

-   Структура: `[Tophash x 8] [Key x 8] [Value x 8] [Overflow Pointer]`
-   Ключи и Значения хранятся **отдельно** (`[8]Key [8]Value`), а не парами `Key-Value`. Это исключает паддинг (байты-пустышки для выравнивания памяти процессором).
