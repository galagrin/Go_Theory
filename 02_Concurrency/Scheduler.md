# Go Runtime: Глубокое погружение в горутины

## Модель G-M-P (с Go 1.1+)

| Буква         | Что это              | Роль                                            |
| :------------ | :------------------- | :---------------------------------------------- |
| G (Goroutine) | Сама горутина        | Структура с стеком, указателем на код, статусом |
| M (Machine)   | Поток ОС             | Реально выполняет код на CPU                    |
| P (Processor) | Логический процессор | Контекст планирования, очередь горутин          |

## 1. Work Stealing — как P воруют горутины друг у друга

### Зачем это нужно

У каждого `P` есть своя **локальная очередь** горутин (run queue).  
Если один `P` закончил все свои горутины, а у других ещё полно работы — он не должен простаивать.

### Как устроено

У каждого `P` есть:

-   Локальная очередь (обычно до 256 горутин)
-   Доступ к **глобальной очереди**

Алгоритм поиска работы у `P` (упрощённо):

1. Посмотреть в свою локальную очередь
2. Посмотреть в глобальную очередь
3. Попробовать **украсть** горутины у другого `P`
4. Проверить netpoller (есть ли готовые сетевые события)
5. Если совсем ничего нет — `P` может «уснуть»

### Как происходит воровство

-   `P` выбирает случайного «жертву»
-   Пытается забрать примерно **половину** горутин из её локальной очереди
-   Это уменьшает contention и лучше балансирует нагрузку

### Важные следствия

-   Горутины не привязаны навсегда к одному ядру/потоку
-   Порядок выполнения горутин **не гарантирован**
-   Локальные очереди сильно уменьшают конкуренцию за глобальные блокировки

## 2. Системные вызовы — что происходит с M и P

Когда горутина делает блокирующий системный вызов (файл, DNS, старый блокирующий network и т.д.):

### Последовательность

1. Горутина `G` выполняется на потоке `M`, у которого есть `P`
2. `G` входит в syscall → статус становится `_Gsyscall`
3. Runtime **отсоединяет P от M**
    - `P` становится свободным
    - Его можно отдать другому потоку `M`
4. Поток `M` вместе с `G` блокируется в ядре ОС
5. Когда syscall завершается:
    - `G` хочет продолжить выполнение
    - Она пытается найти свободный `P`
    - Если нашла — продолжает выполнение
    - Если не нашла — встаёт в очередь и ждёт

### Зачем так сделано

Если бы `P` оставался занятым на время syscall, то при 1000 блокирующих вызовах тебе понадобилось бы 1000 потоков ОС.  
А так `P` (логически процессор) быстро освобождается и может обслуживать другие горутины.

> Именно поэтому Go хорошо переносит большое количество блокирующих операций — количество `P` остаётся ограниченным.

## 3. GOMAXPROCS — что реально меняет

```go
runtime.GOMAXPROCS(n)
```

Что это такое?

GOMAXPROCS = количество P (логических процессоров).

**По умолчанию:
GoGOMAXPROCS = runtime.NumCPU()**

#### Что оно ограничивает:

-   Максимальное количество горутин, которые могут реально выполняться параллельно на CPU
-   Не ограничивает общее количество горутин
-   Не ограничивает количество потоков ОС (M) напрямую (их может быть больше)

#### Примеры

| GOMAXPROCS          | Смысл                                                                  |
| :------------------ | :--------------------------------------------------------------------- |
| 1                   | "Все горутины работают конкурентно, но не параллельно (на одном ядре)" |
| = числу ядер        | Максимальный CPU-параллелизм                                           |
| Очень большое число | Обычно бесполезно и даже вредно (лишние накладные расходы)             |

**Важный момент**

Даже при GOMAXPROCS=1 программа остаётся конкурентной: горутины быстро переключаются.

Но на нескольких ядрах они уже не будут считать одновременно.

## 4. Статусы горутины

### Основные состояния G:

| Статус       | Значение                                                       |
| :----------- | :------------------------------------------------------------- |
| \_Gidle      | Только что создана, ещё не инициализирована                    |
| \_Grunnable  | Готова к выполнению, лежит в очереди                           |
| \_Grunning   | Прямо сейчас выполняется на M                                  |
| \_Gsyscall   | Находится внутри системного вызова                             |
| \_Gwaiting   | Заблокирована (канал, select, WaitGroup, I/O, парковка и т.д.) |
| \_Gdead      | Завершилась, можно переиспользовать или освободить             |
| \_Gcopystack | Прямо сейчас идёт копирование стека (рост/уменьшение)          |

### Жизненный цикл (упрощённо)

```
создание → _Grunnable → _Grunning ⇄ _Gwaiting
                              ↓
                         _Gsyscall
                              ↓
                            _Gdead
```

## 5. Парковка и распарковка горутин

### Park (парковка)

Когда горутине нечего делать (ждёт данные из канала, ждёт I/O, ждёт таймер и т.д.), runtime её паркует:

-   Статус → \_Gwaiting
-   Горутина снимается с P/M
-   Больше не занимает поток ОС

Это очень дёшево по сравнению с блокировкой потока ОС.

### Unpark (распарковка / wake-up)

Когда событие произошло (пришли данные в канал, сеть готова, таймер сработал):

-   Горутину переводят в \_Grunnable
-   Кладют в очередь какого-то P
-   Рано или поздно планировщик её выполнит

Важные функции runtime (для понимания)

gopark — припарковать текущую горутину
goready / ready — сделать горутину снова runnable

**Именно через park/unpark работают каналы, select, Mutex, WaitGroup, таймеры и netpoller.**

## 6. Netpoller — почему тысячи соединений не требуют тысяч потоков

Проблема классического подхода
В обычной блокирующей модели:

10 000 соединений = 10 000 потоков ОС
Каждый поток жрёт память и дорого переключается

#### Как делает Go

У runtime есть встроенный netpoller, который использует механизмы ОС:

-   -Linux → epoll
-   -macOS/BSD → kqueue
-   -Windows → IOCP

#### Как это выглядит

-   Горутина делает conn.Read()
-   Данных пока нет → горутина паркуется (не занимает M)
-   Netpoller регистрирует сокет в epoll/kqueue
-   Когда данные приходят, ОС уведомляет netpoller
-   Netpoller находит соответствующую горутину и делает ей unpark
-   Горутина продолжает выполнение

#### Результат

100 000 сетевых соединений ≈ небольшое количество потоков ОС
Большинство горутин просто висят в состоянии \_Gwaiting
Один netpoller обслуживает огромное число сокетов

Именно поэтому один небольшой Go-сервис может держать десятки/сотни тысяч keep-alive соединений.

## 7. Concurrency vs Parallelism в терминах Go

### Concurrency (конкурентность)

Структура программы.

Ты умеешь работать с несколькими задачами одновременно (в смысле — задачи прогрессируют, переключаясь друг с другом).
Пример:

10 000 горутин, которые ждут сеть
При GOMAXPROCS=1 они всё равно конкурентны

**Concurrency — это про композицию независимых задач.**

### Parallelism (параллелизм)

Реальное одновременное выполнение на нескольких ядрах CPU.
Пример:

Тяжёлые CPU-bound расчёты
При GOMAXPROCS=8 на 8-ядерной машине они могут считаться по-настоящему параллельно

**Parallelism — это про одновременное исполнение.**

     Concurrency — это то, что дают горутины и каналы.
     Parallelism — то, что даёт планировщик + несколько P (GOMAXPROCS > 1).
