# sync.WaitGroup: Как это работает

Под капотом sync.WaitGroup — это потокобезопасный счетчик с тремя основными методами:

-   Add(delta int): Увеличивает счетчик активных задач на delta.

-   Done(): Уменьшает счетчик на 1 (вызывается при завершении работы горутины, обычно через defer).

-   Wait(): Блокирует горутину, в которой вызван, до тех пор, пока счетчик не станет равен 0.

```go
package main

import (
    "fmt"
    "sync"
    "time"
)

func worker(id int, wg *sync.WaitGroup) {
    // 3. Уменьшаем счетчик при выходе из функции
    defer wg.Done()

    fmt.Printf("Воркер %d начал работу\n", id)
    time.Sleep(time.Second)
    fmt.Printf("Воркер %d закончил работу\n", id)
}

func main() {
    var wg sync.WaitGroup

    for i := 1; i <= 3; i++ {
        // 1. Увеличиваем счетчик СТРОГО до запуска горутины!
        wg.Add(1)
        go worker(i, &wg) // 2. Передаем WaitGroup ПО УКАЗАТЕЛЮ!
    }

    // 4. Ждем, пока счетчик станет равен 0
    wg.Wait()
    fmt.Println("Все воркеры завершили работу!")
}
```

## ⚠️ Три главных «грабли» с sync.WaitGroup на собеседованиях

### 1. Передача sync.WaitGroup по значению (копирование):

В Go структуры передаются по значению. Если передать wg в функцию без указателя (func worker(wg sync.WaitGroup)), скопируется текущий счетчик. Воркер будет уменьшать свою копию, а main на wg.Wait() зависнет в Deadlock навсегда.

**Правило**: WaitGroup всегда передается строго по указателю (\*sync.WaitGroup).

### 2. Вызов Add() ВНУТРИ горутины:

Если написать

```go
go func() { wg.Add(1); ... }()
```

возникнет Состояние Гонки.

Функция main может дойти до wg.Wait() раньше, чем горутина успеет выполниться и вызвать Add(1). В итоге main просто завершится, не дождавшись фоновых задач.

**Правило**: Add() вызывается до ключевого слова go.

### 3. Отрицательный счетчик (Panic):

Если вызвать Done() больше раз, чем было сделано Add(), счетчик уйдет в минус и Go выбросит панику: panic: sync: negative WaitGroup counter.

## Race Condition (Состояние гонки) и Data Race

Поскольку горутины выполняются параллельно на разных ядрах процессора, возникновение одновременного доступа к общей памяти — частая проблема.
В чем разница между Race Condition и Data Race?

-   Data Race (Гонка данных): Ситуация на уровне памяти/инструкций процессора, когда две или более горутины одновременно обращаются к одной переменной, причем хотя бы одна из них выполняет запись, и между ними нет никакой синхронизации (мутексов, каналов).

-   Race Condition (Состояние гонки): Логическая ошибка в архитектуре приложения, когда порядок выполнения операций горутинами влияет на конечный правильный результат.

Пример Data Race (Счетчик ресурсов):

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    var counter int
    var wg sync.WaitGroup

    for i := 0; i < 1000; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            counter++ // ❌ DATA RACE! 1000 горутин одновременно читают и пишут в counter
        }()
    }

    wg.Wait()
    fmt.Println("Counter:", counter) // Результат будет случайным! (например, 942 вместо 1000)
}
```

### Почему counter++ не является атомарной операцией?

На уровне процессора counter++ состояит из 3 шагов:

-   Прочитать значение из RAM в регистр процессора.

-   Прибавить 1 в регистре.

-   Записать значение обратно из регистра в RAM.

    Если Горутина №2 прочитает значение из RAM до того, как Горутина №1 запишет туда свой результат, изменения одной из них просто затрутся.
