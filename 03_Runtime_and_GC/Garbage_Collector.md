# Garbage Collector в Go: Tri-color Concurrent Mark & Sweep

Сборщик мусора в Go является **необъектным (Tracing), параллельным (Concurrent), трехцветным (Tri-color) Mark & Sweep** сборщиком с минимальными паузами **STW (Stop-The-World)** — обычно менее **1 миллисекунды**.

---

## 1. Базовый алгоритм: Трёхцветная маркировка (Tri-color Abstraction)

На этапе маркировки все объекты в куче (Heap) делятся на три абстрактных цвета:

-   [Белые (White)] ─── Неизвестно / Мусор (Кандидаты на удаление)
-   [Серые (Grey)] ─── Достижимы, но их ссылки ЕЩЕ НЕ проверены
-   [Черные (Black)] ─── Достижимы, и все их ссылки УЖЕ проверены

---

### Как проходит цикл маркировки?

1. **Инициализация:** Все объекты в куче изначально помечаются **Белым** цветом.
2. **Поиск Корней (GC Roots):** Сборщик сканирует глобальные переменные, указатели на стеках всех горутин и регистры. Объекты, на которые они указывают напрямую, перекрашиваются в **Серый** цвет.
3. **Обход графа:**
    - Сборщик берет **Серый** объект из очереди.
    - Находит все объекты, на которые этот серый объект ссылается.
    - Если ссылаемый объект **Белый**, он перекрашивается в **Серый**.
    - Сам исходный объект перекрашивается в **Черный**.
4. **Завершение:** Процесс повторяется, пока не останется **ни одного Серого объекта**.
5. **Очистка (Sweep):** Все объекты, оставшиеся **Белыми**, признаются недостижимым мусором и подлежат уничтожению/освобождению памяти.

---

## 2. Параллельное выполнение и Write Barrier (Барьер записи)

Поскольку Go проводит фазу маркировки **параллельно (concurrently)** с работой основного кода программы (Mutator), возникает смертельная опасность:

> **Сценарий гонки:**  
> Пока GC сканирует объекты, основная программа (мутатор) может оторвать ссылку у Белого объекта от Серого и прикрепить её к Черному объекту.  
> В результате GC подумает, что Белый объект недостижим (ведь у Черного он больше ничего не ищет!), и ошибочно удалит **живые данные**.

### Решение: Write Barrier (Барьер записи)

Чтобы этого не произошло, при включении фазы маркировки Go активирует **Write Barrier** (с Go 1.8 используется **Hybrid Write Barrier**).

-   **Как работает:** Это специальная инструкция, встраиваемая runtime при любой записи указателя в память.
-   Если во время работы GC программа пытается записать ссылку на Белый объект в Черный объект, Write Barrier моментально перекрашивает Белый объект в **Серый**, гарантируя, что GC его не пропустит.

## 3. Фазы цикла Сборщика Мусора

Полный цикл GC состоит из 4 этапов:

[1. Sweep Termination] ──> [2. Mark Phase] ──> [3. Mark Termination] ──> [4. Sweep Phase]
(STW ~микросекунды) (Concurrent + WB) (STW < 1ms) (Concurrent)

1. **Sweep Termination (STW):** Крошечная пауза Stop-The-World для завершения предыдущего цикла очистки и включения Write Barrier.
2. **Mark Phase (Concurrent):** Основная фаза. GC использует **25% вычислительной мощности CPU** (`GOMAXPROCS * 0.25`) для параллельной маркировки объектов. Программа продолжает работать.
3. **Mark Termination (STW):** Короткая пауза Stop-The-World. Завершается маркировка, выключается Write Barrier, вычисляется размер следующей цели GC.
4. **Sweep Phase (Concurrent):** Параллельная очистка памяти. Память освобождается фоново по мере необходимости, когда горутины запрашивают новые аллокации.

## 4. Настройка и Управление GC (`GOGC` и `GOMEMLIMIT`)

В Go нет десятков сложных флагов настройки GC, как в Java. Главные инструменты управления:

### ① Переменная `GOGC` (по умолчанию `100`)

Определяет коэффициент роста кучи в процентах перед запуском следующего цикла GC.

-   `GOGC=100`: Новый цикл закроется, когда размер живой кучи вырастет на **100%** (в 2 раза) относительно размера после предыдущей сборки.
-   `GOGC=200`: GC запускается реже (когда куча вырастет в 3 раза) — экономит CPU, но расходует больше RAM.
-   `GOGC=off`: Полностью отключает сборку мусора.

### ② `GOMEMLIMIT` (Появился в Go 1.19)

Задает **жесткий лимит памяти** для Go-процесса (например, `GOMEMLIMIT=2GiB`).

-   Помогает избежать падения сервисов в Kubernetes по OOM (Out Of Memory).
-   Когда память подбирается к лимиту, Go автоматический увеличивает частоту вызовов GC, чтобы удержаться в рамках лимита.

## 💡 Чек-лист

1. **Какой алгоритм у GC в Go?** — Concurrent Mark-Sweep на базе трехцветной маркировки (Tri-color marking) и Hybrid Write Barrier.

2. **Есть ли STW в Go?** — Да, но их два, и они суммарно занимают **меньше 1 миллисекунды** (только на старт и финал маркировки).

3. **Сколько ресурсов CPU забирает GC?** — По умолчанию фиксированно **25% от доступных ядер CPU** во время фазы маркировки.

4. **Что такое GC Pacer?** — Внутренний алгоритм runtime, который динамически рассчитывает момент старта GC, чтобы куча не превысила лимит `GOGC` в момент завершения маркировки.
